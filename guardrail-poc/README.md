# LLM Guardrail POC — TypeSafe Jev via OpenRouter

A proof-of-concept for the use case TypeSafe's blog post names directly
(`typesafe.ai/blog/introducing-system-one-models-and-jev`): **"Verify
everything. Score, judge, verify, guardrail, and detect jailbreaks of LLM
prompts, reasoning traces, and/or outputs."** It scans a batch of chat
messages — both inbound user prompts and outbound assistant responses — for
safety/policy hazards using Jev, then applies a code-owned verdict.

This follows TypeSafe's own `cookbooks/llm_guardrails.md` recipe: one call
per message, several parallel hazard questions plus an overall severity
score, no per-hazard round trip.

## Dataset

`messages/messages.json`, generated by `generate_messages.py` from 10
templates covering both inbound and outbound traffic for a
customer-support-style chatbot: benign questions, jailbreak attempts (roleplay
framing, "ignore instructions"), harmful requests, sensitive-data requests and
leaks, policy-violating responses (medical/financial overreach), and a
correct safety refusal.

```bash
python generate_messages.py --items 200 --seed 42
```

This **wipes and rebuilds** `messages/messages.json`. `--seed` makes it
reproducible.

**Content note**: jailbreak/harmful templates use only abstract test-fixture
phrasing (the kind used in standard safety-classifier eval sets) — never real
harmful instructions. Sensitive-data templates use `Faker`-generated fake
SSNs/card numbers, never real data.

## How it scans (map step)

One call per message, five parallel questions over `state = {"role", "text"}`:

- `jailbreak_attempt` (**Noul**) — roleplay/prompt-injection/"ignore
  instructions" style bypass attempts.
- `harmful_request` (**Noul**) — requests or provides clearly harmful content.
- `sensitive_data_exposure` (**Noul**) — contains or requests SSNs, card
  numbers, credentials, etc.
- `policy_violation` (**Noul**) — definitive medical/legal/financial claims,
  or unauthorized promises/guarantees.
- `severity` (**Score**, 4 levels: none → mild → serious → severe) — a
  holistic overall risk level.

All messages are scanned concurrently (`ThreadPoolExecutor`, 40 workers,
progress every 50) against a shared, connection-pooled, auto-retrying
`requests.Session` (see `jev_client.py`); a per-message failure is caught and
reported rather than aborting the batch.

## Verdict (code-owned, not the model)

- `severity >= 2` and `confidence >= 0.5` → **BLOCK**.
- `severity >= 2` and `confidence < 0.5` → **NEEDS_HUMAN_REVIEW** (per
  TypeSafe's [confidence guidance](https://docs.typesafe.ai/confidence): a
  high-severity call made with low confidence shouldn't be auto-blocked
  outright).
- Any individual hazard Noul `> 0.6` but severity `< 2` → **FLAG** (logged,
  not blocked).
- Otherwise → **ALLOW**.

## Setup

```bash
pip install -r requirements.txt
cp .env.example .env
# edit .env and set OPENROUTER_API_KEY
```

## Run

```bash
python generate_messages.py         # build/rebuild the dataset (defaults: 200, seed 42)
python scan_messages.py             # report + BLOCK/NEEDS_REVIEW detail (capped at 15)
python scan_messages.py --verbose   # also print every message's verdict + full detail list
```

Prints verdict counts (ALLOW/FLAG/BLOCK/NEEDS_HUMAN_REVIEW), hazard trip
rates per question, an inbound-vs-outbound role breakdown, and the list of
blocked/needs-review messages.

A well-behaved run should show: jailbreak templates tripping
`jailbreak_attempt`, harmful-request templates tripping `harmful_request`,
sensitive-data templates tripping `sensitive_data_exposure`, policy-violation
templates tripping `policy_violation` — and, importantly, the
`safe_refusal_output` template scoring `ALLOW` despite discussing a sensitive
topic, since it correctly refuses rather than complies. That last case is
the real test of whether Jev is judging *compliance*, not just flagging
messages that mention a sensitive keyword.

## Notes

- `jev_client.py` is the same adapter used across all POCs in this
  repo (shared, connection-pooled, auto-retrying `requests.Session` hitting
  OpenRouter's `POST /api/alpha/decisions`), with `POOL_SIZE`/`MAX_WORKERS`
  sized down for this POC's smaller default dataset — concurrency was
  already stress-tested up to 300 concurrent workers in
  `email-classification-poc` with zero errors, so both are easy to raise here
  if the dataset is scaled up.
- The generator stores which template produced each message purely for your
  own verification; that field is never sent to Jev.
